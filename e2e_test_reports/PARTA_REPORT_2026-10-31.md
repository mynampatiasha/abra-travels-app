## Bugs / findings
- BUG-1 (Major) POST /api/roster/customer/bulk uses users.findOne({firebaseUid: JWT userId}) (routes/roster_router.js ~line 249). After Firebase removal the JWT userId is the Mongo _id, so the lookup is empty and every customer gets 400 "Admin organization not found". The customer app also calls this endpoint (roster_repository.dart:236).
- BUG-2 (Minor/Design) A one-day roster (fromDate == toDate) is rejected: "End date must be after start date".
- BUG-3 (Major data/UX) Dashboard "Pending Rosters" = 73 (counts status=pending_assignment) but the Pending Rosters screen shows 5. All 68 real "pending" rosters already carry a vehicle/driver/trip id and have end dates in the past, so the screen hides them; the dashboard number is misleading.
- OBS-4 Dashboard "Total Drivers" shows 0 although 3 real drivers exist ("Active & Available" may exclude them; check status values).
- OBS-5 Dashboard "Total Customers" 95 while the customers collection holds 100 after adding 5 E2E accounts (check what is counted).
- OBS-6 Registration form: Branch/Location is free text; Department list comes from DB; the form also allows self-registration as Driver (relevant to Part B).
- OBS-7 5 real rosters were cancelled by admin@abrafleet.com during this session (not by the test). Confirm intentional; reversible (soft-cancel).
- BUG-4 (BLOCKER for driver onboarding) Drivers created through POST /api/admin/drivers store the email only at personalInfo.email (no top-level email/name/phone), but login (routes/jwt_router.js ~line 462) does findOne({email}) on top-level email, so these drivers can never log in even with a valid password hash. The 3 real drivers have top-level email/name/phone. Fix belongs in the create-driver route (store lower-cased top-level email, name, phone) and/or the login lookup - hand to the Part B session.
- OBS-4 resolved: the 3 real drivers have status inactive, so the dashboard Total Drivers (Active & Available) shows 0; the two new E2E drivers are active.
- OBS-8 Vehicle registration must match the Indian format (KA01AB1234); a test vehicle named E2E-KA01-0001 is rejected (validation works). Possible data inconsistency: assign-vehicle stores driver.assignedVehicle as an ObjectId, while GET driver details looks vehicles up by vehicleId code (admin-drivers.js ~line 126) - verify in the driver detail screen.
- Security note: client-supplied status on /api/auth/register is ignored/overridden (good).

## Assignment-flow bugs found 2026-10-31 (file: abra_fleet_backend/routes/route_optimization_router.js)
- BUG-5 (BLOCKER) POST /api/admin/drivers/:code/assign-vehicle stores only an `assignedDriver` object on the vehicle. /assign-optimized-route (~lines 1008-1010) reads the flat fields assignedDriverEmail / driverId / assignedDriverId / driverName, so such a vehicle fails with DRIVER_NOT_FOUND. Real vehicles have the flat fields. Test workaround: copied the flat fields onto the 2 E2E vehicle docs only.
- BUG-6 (CRITICAL) After a SUCCESSFUL assignment the rosters stay `pending_assignment` with no vehicle/driver/tripId. Cause (code + DB evidence; server log not seen): `needsBothTrips` is a `const` declared inside the per-date loop (line 1618, loop lines 1539-1908) but used at line 1966 in the roster update outside the loop -> ReferenceError, swallowed by the try/catch at line 2000. Trips, vehicle and notifications ARE written. Effects: Pending screen keeps showing assigned customers (can be double-assigned), assigned-trips/customer views do not show them, driver/customer notifications claim an assignment that the roster does not reflect. Likely explains the 68 real rosters that carry vehicle/driver/trip ids but are still "pending" (BUG-3) - to confirm.
- BUG-7 (MAJOR) compatible-vehicles company check (lines 650-655) reads `trip.customerEmail`, which trips do not have (emails are in stops[].customer.email) -> "Vehicle has unknown" -> every vehicle with any trip is "Company mismatch" for everyone, including the same company. Vehicle sharing and the consecutive-trip validation can never run.
- BUG-8 (MAJOR) capacity: (a) compatible-vehicles marks every vehicle with no assignments as compatible before any capacity/company check (lines 631-641) - 4 pax into a 3-seat car and two companies together are accepted; the 3-seat car shows seats=3 incl. driver, 2 usable; (b) /assign-optimized-route checks existing seats only for scheduledDate = TODAY (line 1160, also lines 1225 and 2401), so for future dates cumulative overbooking passes (4th passenger accepted on a 3-passenger car) and vehicle.assignedCustomers stays empty.
- BUG-9 (MAJOR) A second assignment to the same vehicle/date creates a second trip document with the same tripGroupId instead of pooling stops; the group driver pipeline (updateMany over vehicle+type+date+driver) will then act on both trips together.
- BUG-10 (MAJOR) No server-side company check: a customer from another company is accepted on the same vehicle (UI only protects via compatible-vehicles, which is itself broken - BUG-7/8a).
- BUG-11 (MEDIUM) POST /api/roster/optimize and /assign-bulk are stubs (mock distance, one driver per roster, drivers from `users`, ignores vehicles/capacity). Not used by the live Pending screen but still exposed to any authenticated user and /assign-bulk would notify real drivers.
- BUG-12 (MEDIUM) rosterType is taken from the request body (not the roster document): a request without it creates both pickup and drop trips for a logout-only customer (this happened in the test because the test payload omitted it - the real UI sends it, but the server should read it from the roster).
- No server rule found for: driver on leave, driver who declined, driver already on overlapping trips (time-slot check also uses today's date, line 1225), roster status must be pending (re-assigning is allowed on purpose).
- OBS performance: first assign call took 65 s (2 customers x 5 days; one insert/update round-trip per trip with transactions over the Mumbai Atlas link); the UI would sit on a spinner and a 40 s client timeout would show an error although the data is written.
